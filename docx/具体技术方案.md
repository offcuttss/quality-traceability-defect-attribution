# 星衡精密 · 质量追溯与缺陷归因智能体系统 — 具体技术方案

> 配套文件：`技术方案提示词.md`（总控约束）。本方案与之冲突时以提示词文件为准。
> 版本：v1.0（2026-11-12）· 技术栈与数据红线锁定，后续阶段不得变更。

## 1. 总体架构

```
┌────────────────────────────────────────────────────────────┐
│                    FastAPI 应用层 (port 8000)               │
│   统一返回 {"ok", "data", "error":{code,msg}}               │
│   权限中间件（角色→数据矩阵校验，f41）                        │
├────────────────────────────────────────────────────────────┤
│                    Agent Harness（自研编排层）               │
│  工具注册表 → 意图路由 → 工具调用 → 置信度门限 → 人工确认拦截   │
│  触发条件检测器：断链/缺依据/版本冲突/系统不可用 → 转人工（f44） │
├──────────────┬──────────────────┬──────────────────────────┤
│  知识库层     │                  │                          │
│  知识图谱     │  归因引擎（只读） │  追溯引擎（只读）          │
│  SQLite+nx   │  Ollama 本地 LLM  │  批次链路 / 断链检测       │
│  向量索引     │  归因提示/风险标记 │  待刷新/快照兜底(f34/f35)  │
├──────────────┴──────────────────┴──────────────────────────┤
│                  SQLite 业务库（单文件 starheng.db）          │
│  users / batches / inspections / reworks / audit_log /      │
│  manual_queue / snapshots / kg_nodes / kg_edges / vectors   │
└────────────────────────────────────────────────────────────┘
```

**核心原则**：写路径（放行/签核/根因认定）永远不经过 AI；AI 输出只进"建议"表，且必须带事实引用。

## 3. 知识图谱设计（本地部署）

**节点类型**（存 `kg_nodes`：id, type, name, version, props_json）：
- `Batch`（批次，含原批号/换批号关联）、`Machine`（机台）、`Part`（两类试点零件）、`Tool`（刀具）、`ProcessVersion`（工艺版本）、`Gauge`（量具，含校准状态）、`DefectCase`（缺陷事件）、`Person`（角色账号）。

**边类型**（存 `kg_edges`：src, dst, rel, valid_from, valid_to, source_ref）：
- `produced_on`（批次→机台）、`measured_by`（检测→量具）、`reworked_to`（批次→批次，**换批号强制关联边，缺此边=断链**，f11）、`governed_by`（批次→工艺版本）、`caused_by`（缺陷→候选原因，**仅 AI 提示，置信度门限以下不落边**）、`certified_by`（量具→校准证书，过期则节点标 stale）。

**构建与更新**：每天两次快照窗口（f34）触发 `builder.py` 增量重建；图谱查询结果一律携带 `data_time`（数据时点）与 `version`。

**向量通道**：归因建议检索用——把"事实引用片段"（检测量值摘要、返工单摘要）做 embedding 存 `vectors` 表，检索时与图谱结果融合（图谱给结构证据，向量给相似案例），两者都进建议的"事实引用"字段（f45）。

## 4. Agent Harness 设计（自研，不用重型框架）

```
请求 → 权限校验(auth.py) → Harness.engine
  1. 意图路由：关键词+规则匹配注册表中的工具（trace/diagnose/snapshot）
  2. 前置红线：redlines.check_pre() —— 歧义记录不进推荐样本(f33)
  3. 工具执行：只读查询 + KB 检索
  4. LLM 归因：Ollama 生成提示与风险标记，输出必须含事实引用
  5. 置信度门限：低于 config.yaml 阈值 → 直接转人工，不展示建议
  6. 触发条件检测：断链/缺依据/版本冲突/系统不可用 → escalate 落库三要素
  7. 后置红线：redlines.check_post() —— 建议只写建议表，永不写放行/签核字段
  8. 审计落库：六字段完整写 audit_log（f45）
```

**人工确认拦截点**：engine 中所有"确认类"动作（接手确认、复核发起、签核）返回 `status="WAIT_HUMAN"`，由对应角色调确认接口完成，系统不代填。

## 5. 数据库核心表

| 表 | 关键字段 |
|---|---|
| users | id, name, role, active（角色枚举=六角色） |

| inspections | id, batch_no, gauge_id, value_json, unit, tolerance_version, ambiguous(bool), event_time |
| reworks | id, batch_no, original_batch_no, tool_id, reason |

| snapshots | biz_no, snapshot_json, taken_at, stale(bool) |

## 7. 对外接口（统一返回结构）

| 接口 | 角色 | 说明 |
|---|---|---|
| POST /api/trace/query | 授权岗位 | 追溯清单查询（含数据时点/版本/待刷新标识） |
| POST /api/trace/rework-link | 工艺工程师 | 返工登记，强制校验原批号关联 |
| POST /api/diagnose | 质检员 | 异常定位辅助建议（只读建议，不写处置） |
| POST /api/confirm | 对应审批人 | 人工确认（接手/复核/签核），WAIT_HUMAN 闭环 |
| GET /api/audit/{biz_no} | 产品安全负责人 | 审计链重建 |
| POST /api/kb/rebuild | 质量数据工程师 | 图谱与向量增量重建 |

## 8. 阶段计划（每阶段按【交付要求】四件套交付）

1. **阶段一**：骨架 + 建表 + 权限矩阵 + 统一返回结构。
2. **阶段二**：数据红线模块（放行拦截、断链检测、三要素落库、待刷新/快照）+ pytest。
3. **阶段三**：知识库（图谱构建 + 向量检索 + Ollama 接入）。
4. **阶段四**：Harness 编排 + 追溯/归因两个工具 + 审计链重建接口。
5. **阶段五**：seed 演示数据回放（f11 断链场景等）+ 全链路验证脚本。

## 9. 风险预判

- Ollama 未启动或模型未拉取 → llm.py 必须有降级路径：返回"转人工：关键系统不可用"，不得静默失败。
- networkx 图随数据增长内存上升 → 试点期两类零件数据量小，可接受；预留按 part_type 分图。
- 每行注释会显著拉长代码 → 用紧凑注释风格（行尾 # 注释），不牺牲可读性。
